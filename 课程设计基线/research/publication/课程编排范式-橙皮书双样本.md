- **样本 B**：bozhouDev《ChatGPT 橙皮书》（本地快照 `upstream/09-harness/codex-orange-book/`，8,282 行 / 231 KB）

## 0. 这份文档解决什么

用户诉求原文：**"所有的案例和内容需要高质，然后编排整理，想一门真正的，有始有终，有价值，学习者能够学得下去的课程。"**

本项目已经冻结了三件事：14 卷的知识职责、双载体产品模型、证据与许可纪律。但 **"一门课"不等于"14 个知识板块"**。缺的是编排层：

| 缺口 | 具体表现 | 本文档对应章节 |
|---|---|---|
| 有始无终 | 14 卷有知识路径，但没有"读完了会得到什么"的终点物 | §7、§11 |
| 承诺不明 | 卷首写"职责"（编辑语言），不写"学完能做什么"（读者语言） | §7 |
| 章节无契约 | 现有章节模板完整但只有 2 章在用，未上升为全卷规范 | §8 |
| 案例无编排 | 有 Canonical Case 概念与 EVL 等级，但没有"案例怎么排、排在哪、谁贯穿" | §9 |
| 学不下去 | 无阅读成本标注、无难度曲线设计、无"允许跳读"的显式许可 | §10 |
| 系列无封面 | 14 卷之间没有系列身份、系列统计和卷间导流 | §6 |

本文档把编排层从"感觉"变成 **可执行规范**，并给出 14 卷的总表。

## 2. 样本 A：花叔「橙皮书」系列

### 2.1 系列级设计：12 卷作为一个出版品牌

系列页（`/orange-books/`）在**一屏之内**完成六件事：

```text
系列名       橙皮书 / Orange Book
系列定位     写给每一个想用 AI 做事的人
系列主张     最系统的 AI 编程中文资料，来自真实产品开发与内容创作实践
系列承诺     每一本都免费
系列统计     Published 12本 · Total Pages 994页 · Now Writing 0本
缘起故事     "2024 年底，我用 AI 做了一个 iOS App，上线后冲到了 App Store 付费榜第一。
             我不会写代码，从来都不会。" —— 花叔 · AI Native Coder · 30 万+ 读者
```

然后是 12 张卷册卡片，每张卡片只有四个字段：

| 字段 | 例（Vol. 03） |
|---|---|
| 卷号 | `03` |
| 主标题 | Harness Engineering |
| 副标题（一句话承诺） | 从「和 AI 聊天」到「给 AI 造缰绳」 |
| 阅读成本 | `102 pages` |

卡片带状态位（`Published` / `Coming Soon` / `Now Writing`）。

**关键观察**：

1. **系列统计是可信度机制**。12 本 / 994 页 / 0 本编写中 —— 数字让"系统性"变成可验证的事实，而不是形容词。
2. **缘起故事把作者身份变成学习动机**。"我不会写代码，从来都不会"直接回答了读者最关心的问题：*我这样的人能不能学*。
3. **副标题全部是"从 X 到 Y"或"让 X 变成 Y"**，没有一个是内容清单。例：
   - `一周内用 AI 独立构建一个完整产品`（Vol.01）
   - `拆解 Anthropic 的 AI 产品架构决策`（Vol.02）
   - `从「和 AI 聊天」到「给 AI 造缰绳」`（Vol.03）
   - `让 AI 记住你的工作方式`（Vol.04）
   - `个性化 AI Agent 从入门到精通`（Vol.05）
4. **单卷长度按主题自然长度决定**：36 / 42 / 50 / 63 / 72 / 80 / 95 / 102 / 120 / 232 页。**不做丛书统一厚度**。
5. **卷与卷互相导流**：每个卷页底部有 `Also in This Series`，列出其余 4 卷的标题 + 副标题 + 页数。任何一卷都是入口。
6. **卷内身份连续**：`Vol. 05 · Orange Book Series` 出现在每个卷页页眉。

### 2.2 单卷页面契约：一屏之内回答 7 个问题

每个卷页（抽样：Claude Code / 源码解析 / Harness / Agent Skills / OpenClaw 五卷）结构完全一致：

| 顺序 | 要素 | 作用 |
|---|---|---|
| 1 | 卷号 + 系列名 | 我在读系列里的哪一本 |
| 2 | 主标题 | 讲什么 |
| 3 | 副标题（一句话承诺） | 读完能做什么 |
| 4 | 页数 + 状态 + 作者 | 要花多少成本 |
| 5 | 获取入口（微信读书 / PDF / B站 / YouTube） | 现在就能开始 |
| 6 | `— About · 卷首 —` 一段卷首语 | 承诺边界与读法 |
| 7 | `— Table of Contents · 目录 —` 全部章名 | 精确预期 |

**卷首语写法规律**（三句结构）：

```text
[这是什么文体] + [覆盖范围，用 "从…到…从…到…" 排比] + [读法承诺]
```

例（Agent Skills 卷）：*"从概念到实战的 Agent Skills 完全指南。我自己造了 27 个 Skills，覆盖写作、配图、调研、校审、视频制作等场景。这本书把一手经验整理成体系：安装使用、创建开发、5 种高级设计模式。"*

**注意最后一句是"体系"而不是"技巧集"** —— 学习者买的是结构，不是碎片。

### 2.3 卷内编排的三种模式

抽样 5 卷，发现花叔并非只用一套编排法，而是按"读者会不会顺序读"选择模式：

| 模式 | 样本卷 | 章数 | 结构 | 适用 |
|---|---|---|---|---|
| **教程型（叙事弧）** | Vol.01 Claude Code | 13 | 为什么 → 安装 → 第一个项目 → 工作流 → 扩展 → 协作 → 完整产品 → 心智模型 → 架构 → 附录 | 读者会从头读到尾 |
| **架构分析型** | Vol.02 源码解析 | 12 | 蓝图 → 全景 → 逐子系统（Prompt/工具/权限/记忆/上下文/搜索/多 Agent）→ 未来 → 方法论 | 有经验的读者，按章跳读 |
| **方法论 + 案例型** | Vol.03 Harness | 18 | 概念（1–5）→ **7 个深度案例**（6–12）→ 亲手搭建（13–17）→ 升华（18） | 需要说服 + 需要动手 |
| **教程型（技能）** | Vol.04 Agent Skills | 11 | 进化 → 本质 → 原理 → 生态 → 第一个 → 实战 → 创建 → 高级模式 → 未来 → 附录 | 读者会顺序读 |
| **手册型（分区参考）** | Vol.05 OpenClaw | 35 章 / 8 部 | 认识 → 架构 → 部署 → 渠道 → Skills → 模型 → 安全成本 → 生态 + 附录 ABC | 读者只查需要的部分 |

**最有参考价值的是 Vol.03 的案例型结构**：

```text
01–05  概念建立（是什么 / 六十年简史 / 三次命名 / 五个组件 / 减法哲学）
06–12  七个深度案例：OpenAI Codex · Mitchell Hashimoto · Anthropic ·
       Stripe Minions · LangChain · Kent Beck · 花叔自己
13–17  亲手搭建（从空白开始 → 指令层 → 约束层 → 能力层与记忆层 → 编排层）
18     升华（经验工程：谁来设计下一代的缰绳）
```

三个可迁移要点：

1. **概念不超过 5 章**，然后立刻进案例。不让读者在抽象里待太久。
2. **案例数量是 7 个，且有层次**：大厂工程（OpenAI / Anthropic / Stripe）、开源社区（LangChain）、个人方法论（Mitchell Hashimoto / Kent Beck）、**作者自己**。
3. **最后一个是作者自己的案例，用来把"他们能做到"翻译成"我也能做到"**。
4. **案例之后必须有"从空白开始"的亲手环节**，否则读者只会评论，不会做。

Vol.02 的收束方式也值得注意：**最后一章不是总结，而是方法论迁移**（`12 Harness Engineering 方法论`）。Vol.05 最后一章同理（`12 龙虾纪元`）。

### 2.4 章级解剖：OpenClaw 卷页面级证据

对 114 页 PDF 做逐页文本提取与页码映射（`pymupdf`，78,007 字符），得到硬数据：

| 指标 | 数值 |
|---|---|
| 总页数 | 114 |
| 正文页（第 5–105 页，35 章） | 101 页 |
| 每章平均页数 | **2.9 页** |
| 每页平均字符 | **672** |
| 每页字符区间 | 92 – 1234 |
| `注意` callout | 40 处 |
| `核心建议` callout | 29 处 |
| 每章平均 callout | **≈ 2 处** |
| 章末"小结" | **0 处** |

**章节解剖模板**（35 章高度一致）：

```text
[章号] [中文标题]
[英文标题]
[一句话承诺 —— 30~50 字，句式："X 是一个…，它让…" 或 "从 A 到 B，…"]

[散文 2–4 段：为什么 / 是什么]

[结构载体，三选多]
  · 对比表（表格几乎每页都有）
  · 层级表（角色 / 职责 / 关键细节）
  · 箭头流程（用户发消息 → Channel 接收 → Gateway 路由 → Agent 处理 → Node 执行 → 回复用户）
  · 代码块（可直接抄的配置与命令）

[判断 callout，每章 1–3 个]
  · 注意 —— 风险、坑、边界
  · 核心建议 —— 推荐做法
  · 为什么这很重要？ —— 原理级解释
```

**关键设计判断：全书没有一处"本章小结"。** 原因是它的章足够短（2.9 页），读者读完即消耗完毕，小结反而是冗余。判断信息全部压在 `注意` / `核心建议` callout 里，跟事实陈述在视觉上分层。

**极少量地使用视觉强调**：正文几乎不加粗（全书仅 61 行含粗体），强调交给表格列名与 callout 标题。

### 2.5 版次、声明与勘误纪律（PDF 第 1 页）

封面页即"信任页"，字段清单：

```text
信息来源      OpenClaw 官方文档 · GitHub 仓库 · 社区调研
文档版本      v1.4.0
适用版本      v2026.3.13
发布时间      2026-03-24 (build #1)
涵盖内容      架构原理 · 部署指南 · 渠道接入 · Skills系统 · 模型配置 · 安全与成本 · 生态全景
作者与渠道    花叔 / B站 / YouTube / 公众号 / 知识星球
撰写方式声明  "本文档在 Claude Code 辅助下整理编写，内容的准确性与时效性仅供参考"
勘误入口      "如有勘误或建议，欢迎关注公众号「花叔」反馈交流"
配套与更新    "配套视频教程：B站「OpenClaw从0到1」· 后续更新：飞书文档"
```

**三个日期字段严格分离**：`文档版本`（书的语义版本）、`适用版本`（被描述产品的版本）、`发布时间`（资料截止）。这一点与本项目 `05-网站与蓝皮书双载体出版范式.md` 的 `edition / source_commit / evidence_cutoff` 三元组同构，可以互相印证。

**数字一律带时间戳**：正文出现 `核心数据快照 截至 2026年3月24日`，把动态事实圈成有日期的快照，而不是伪装成长期事实。这正是本项目 `Stable Core / Current Practice / Frontier Snapshot` 分层的通俗化表达。

**尾页是转化页，不是结束页**：第 114 页放作者介绍、知识星球入口、B 站 / YouTube / 公众号、下一步更新入口。**课程以"接下来去哪"结束，而不是以最后一个知识点结束。**

### 2.7 样本 A 结论

**可吸收**

- 系列身份系统（系列名 / 定位 / 统计 / 缘起 / 互导）
- 卷册卡片的四字段契约（卷号 + 主标题 + 一句话承诺 + 阅读成本 + 状态）
- 三种卷内编排模式的选择方法
- 案例型结构（概念 ≤5 章 → 7 个分层案例 → 亲手搭建 → 方法论升华）
- 章级解剖模板（承诺句 → 散文 → 结构载体 → callout）
- 封面信任页的字段清单
- 尾页转化设计

**不吸收**

- **无许可声明**，不可复用正文。
- **无明确验收标准**。花叔的"学完能做什么"停留在副标题，没有可检查的毕业产物。本项目有 `Artifact + 验收标准`，必须保留并强化。
- **无来源分级**。官方事实、社区信号与作者判断在版式上不区分。本项目有 `Source Definition / Source View / Editorial Synthesis / Proposed Model`。
- **无失败章**。除安全卷外，失败与边界靠 callout 零散承载。本项目课程宪法原则 9 要求"Teach failure"。

## 3. 样本 B：bozhouDev《ChatGPT 橙皮书》

### 3.1 前置件（正文之前，4 个模块）

```text
[标题 + 一句话定位]
[版本表]  版本 v0.2.0 | 最后校验 2026-07-13 | 资料性质：非官方指南，不代表官方文档或产品承诺
[适用声明]  以 2026-07-13 可访问的能力为参考 + 变化警告 + 第三方工具边界说明
[本次更新]  本版新增了什么，以及为什么（含改名说明）
[阅读入口]  在线阅读 / 下载 PDF / 预览（并提示 GitHub 大 PDF 预览会误导）
[目录]  全量锚点
[0. 使用说明]
   0.1 重要声明（非官方 / 以官方为准 / 持续维护 / 优先看 Markdown 原稿）
   0.2 这份 PDF 适合谁（5 条人群）
   0.3 阅读路线（快速上手 / 开发者核心 / 进阶扩展，三条显式路线）
```
**三点值得直接移植**：

1. **"本次更新"放在目录之前**，让回访读者 30 秒内知道要不要重读。
2. **"适合谁"用人群清单而不是抽象描述**（"完全没用过 Codex，但想系统上手的人"）。
3. **"阅读路线"给三条**，并显式写出省略哪些篇 —— 这是"允许跳读"的许可。

### 3.2 三层结构与量化特征

标题体系是 **篇 → 主题 → 问题** 三层，外加 `#####` 作为段落级小标题：

```text
第 X 篇            （5 篇）
  ### 主题         （28 个）
    #### 问题      （145 个）
      ##### 子点   （136 个）
```

量化特征（全文 8,282 行 / 231 KB）：

| 载体 | 数量 | 密度观察 |
|---|---|---|
| 表格行 | 1,214 | **表格是主力信息载体**，平均每 7 行就有一行表格 |
| 图片 | 123 | 案例步骤逐图说明 |
| 代码块 | 274（548 个围栏） | 命令、配置、Agent 指令、Skill 模板 |
| 引用块 | 83 | 用户会说的话 / 关键断言 |
| 分隔线 | 159 | 每个知识点自成一个视觉单元 |
| 含粗体的行 | 61 | **极度克制**，强调交给表格与结构 |

**结构与样本 A 的对照**：样本 A 的章 = 固定长度的独立单元（2.9 页）；样本 B 的 `####` = 一个具体问题，长度随问题自然伸缩（从几行到 200+ 行）。样本 B 的 `####` 标题几乎全是**口语化问句**：

```text
Codex 到底是什么 / Codex 能做什么 / Skill 还是 MCP？什么时候用哪个
Codex 和 ChatGPT 的区别 / Work 和 Codex 的核心区别
新手应该怎么选？ / Sites 不适合做什么？ / 为什么两个界面看起来很像？
```

**这是可迁移的关键技巧**：把"知识点的名字"改成"读者脑子里的问题"。`MCP 协议概述` 不如下面这一句。

### 3.3 主线案例设计

第五篇 5 个案例，**全部围绕同一个虚构项目"宠物零食店"**，逐步长大：

| 案例 | 内容 | 新增能力 |
|---|---|---|
| 一 | 制作宠物零食售卖的前端页面网站 | 计划模式 / 本地预览 / Git 初始化 / 细节迭代 / 推送到 GitHub |
| 二 | 给网站增加功能和优化页面 | 登录注册页 / 分类体系 / 注释式优化 / 购物车确认地址 |
| 三 | 制作管理后台 | 计划模式复用 / 效果检查 / Git 提交 |
| 四 | 制作品牌招商 PPT | 安装 PPT Skill / `/` 调用 Skill / 结果检查 |
| 五 | 制作宣传视频 | 安装视频插件 / 计划生成 / 效果预览 |

**设计价值**：

1. **一个项目贯穿全部案例**，读者不需要每章重新理解背景，认知负担全用在新技术上。
2. **案例递进覆盖不同产物类型**：网页 → 功能 → 后台 → PPT → 视频。从"写代码"扩展到"交付一切"。
3. **每个案例的步骤以"动作 + 图 + 可观察结果"构成**，不是原理复述。
4. **案例是最后一项，不在各章中零散出现**。读法清楚：学完技术，再看怎么串起来。

### 3.4 模板库与附录

- **任务模板库**（`Codex 任务模板库`）：读项目 / 修 Bug / 加功能 / 前端页面 / 代码审查 / 重构 / 写测试 / 写文档 —— 8 个可复制模板，每个带"检查点"表。
- **附录 A：第三方模型接入**。

**模板库的本质**：把"读完就忘的一次性操作"变成"可反复取用的资产"。这是"有价值"最实在的形态 —— 读者一年后回来，还能用。

### 3.5 样本 B 结论

**可吸收**

- 前置件 4 模块（版本表 / 适用声明 / 本次更新 / 阅读路线）
- "适合谁"用人群清单
- 多条阅读路线 + 显式跳读许可
- 用问句做标题
- 结构载体优先（表格 / 图 / 代码 / 引用），散文只做连接
- 一个项目贯穿多个案例的递进设计
- 任务模板库
- 大 PDF 预览提示等"读者体验细节"

**不吸收**

- **无证据等级、无来源记录**。所有陈述同一置信度。
- **无失败模式专章**。
- **GPL/第三方判例未处理**（其附录引入第三方工具时的许可边界需本项目自查）。
- 章节长度无上界，个别 `####` 极长（如 App 基础使用 291 行），与"学得下去"目标冲突。

## 4. 交叉结论：18 条编排规律

### A 组｜系列与导航

1. **系列先于单卷。** 读者先看到"12 本 / 994 页 / 0 本编写中"，再看到某一卷。系列身份是可信度来源，单卷无法替代。
2. **每卷只有一个承诺句**，句式是"从 X 到 Y"或"让 X 变成 Y"，不是内容清单。样本 A 五卷抽样的副标题无一是名词罗列。
3. **卷与卷互相导流。** 每个卷页底部重复出现全系列导航，任何一卷都是入口。
4. **阅读路线显式化，并且显式写出省略什么。** 不是所有读者都读完，但不读的部分必须被命名，否则读者会因为"怕漏"而放弃。

### B 组｜卷内结构

5. **卷内编排模式由"读者会不会顺序读"决定，不由页数决定。** 顺序读 → 教程型叙事弧；按需查 → 手册型分区；需要说服 → 方法论 + 案例型。
6. **卷首必须回答四件事**：适合谁 / 学完能做什么 / 怎么读 / **不包含什么**。第四件是本项目独有优势，样本 A、B 都做得不够。
7. **前置件不超过一屏。** 版本表 + 本次更新 + 阅读入口 + 目录，之后立刻进正文。

### C 组｜章节节奏

8. **章节短、密度高、可单独读懂。** 样本 A 手册型卷每章 2.9 页 ≈ 672 字；每页都有结构载体。
9. **每章以"一句话承诺"开头**，不是以编号或"概述"开头。
10. **叙述让位于结构。** 表格、流程图、命令块承担主要信息传递，散文只做连接与判断。（样本 B：1,214 行表格 / 274 个代码块 / 仅 61 行含粗体）
11. **判断与事实分层。** 样本 A 用 `注意` / `核心建议` callout（35 章共 69 处，约 2 处/章）承载"作者判断"，与事实陈述在视觉上分离。
12. **不强制"本章小结"。** 短章不需要（样本 A 全书 0 处）；只有长而复杂的章节才加收束（样本 B 仅 Work / Sites 两章有"本章总结"）。

### D 组｜可跟做性

13. **案例用同一项目主线递进**，不每章换例子。样本 B 的宠物零食店贯穿 5 个案例，认知负担全部用于新技术。
14. **案例步骤 = 动作 + 图 + 可观察结果**，不是原理复述。
15. **每个案例块必须包含一个失败点或注意事项**，否则读者第一次踩坑就会怀疑教材。
16. **任务模板库把一次性操作变成可复用资产。** 这是"有价值"最实在的形态。

### E 组｜时效、信任与收尾

17. **信任信息前置到封面页**：文档版本 / 适用版本 / 发布时间 / 信息来源 / 覆盖范围 / 撰写方式声明 / 勘误入口，一个都不能藏进附录。
18. **必须以"下一步去哪"结束，而不是以最后一个知识点结束。** 样本 A 尾页放作者渠道、社区与后续更新；样本 B 尾章之后仍有附录和模板库可用。

## 9. 落地规范 D｜案例编排

### 9.1 三类案例，三个位置

| 类型 | 作用 | 出现位置 | 数量 |
|---|---|---|---|
| **Spine Case（贯穿案例）** | 同一真实任务贯穿多章，读者跟着一起长大 | 每卷 1 个，跨 3 章以上 | 1 |
| **Chapter Case（章内案例）** | 本章概念的最小可运行示例 | 章内 `Canonical Case` 节 | 每章 ≤1 |
| **Case Atlas（案例库）** | 同概念的多实现对照与失败样本 | 卷末或专章 | 按证据量 |

**继承规则**：Spine Case 优先复用已有 Canonical Case（如卷 08 的 `CASE-08-01-CALENDAR`），不新建；一个 Spine Case 只能属于一卷，跨卷协作时以"引用 + 增量"表达，不重复讲述。

### 9.2 Spine Case 设计规则

```text
1. 任务是真实的、有输入输出的、可以失败的
2. 复杂度随章节增长（对应样本 B 的"宠物零食店"模型）
3. 每章结束时 Spine Case 都处于可运行状态（不允许中间态损坏）
4. 卷末 Spine Case 的最终形态 = 该卷毕业产物的主体
5. 全程记录 trace / 失败 / 修复，作为失败教学的素材
```

### 9.3 案例卡片字段（与现有 Case Asset Pack 模板一致）

`id / 任务 / 输入 / 预期过程 / 输出 / 失败模式 / 验收标准 / EVL / 复现债务 / 许可`

### 9.4 案例呈现纪律

- 步骤 = **动作 + 图 + 可观察结果**，不写"这时候模型会思考…"式的拟人解释。
- 每个案例块必须含**至少一个失败点**。
- 案例的产物必须可下载或可复现，不能只给截图。

## 10. 落地规范 E｜「学得下去」的六个机制

| # | 机制 | 具体做法 | 约束 |
|---|---|---|---|
| 1 | **短章或章内分段** | 理想节奏：每章 2–4 页 / 15 分钟 | 见 §10.0：达不到理想值时必须以分段读法补偿，不得只是把章写长 |
| 2 | **承诺-交付** | 章首一句话承诺 + 章末验收标准 | 承诺里出现的能力必须能被验收 |
| 3 | **可观察反馈** | 每章至少一个"跑得出、看得见"的结果 | 禁止只用文字描述结果 |
| 4 | **结构代偿** | 表格 / 图 / 命令块承担信息传递 | 连续 600 字无结构载体即视为缺陷 |
| 5 | **允许跳读** | 三条路线 + 每卷卷首"可以跳过什么" + 章节自包含 | 跳读后仍能读懂当前章 |
| 6 | **明确的终点与下一步** | 卷尾毕业产物验收清单 + 下一卷入口 | 禁止以"总结"作为最后一节 |

### 10.0 本项目对「短章」的落地决定（2026-09-10）

**冲突**：样本 A 的章是 2.9 页 / 约 670 字（≈10 分钟）；本项目卷 08 现有章的实测阅读成本是 **60–90 分钟**（正文档位 19–21 KB，`estimated_time: 60-90 minutes`）。本题材的概念层数与证据要求决定了章不可能压到 670 字。

**决定**：不把 60–90 分钟的章强行拆成多个"章"（会破坏 Evidence Packet 与章号的一一对应），而是把"短章"机制下沉到 **章内分段（Reading Sprint）**：

1. 每章章首必须有「本章承诺与读法」，给出 2–3 段的分段表；
2. 每段 **≤25 分钟**，且每段以**可留下的产物**结束，不以"读完了"结束；
3. 必须给出一条"只有一次完整时间"的最小读法，且被跳过的小节不阻塞后续章节；
4. 章内小节标题即分段边界，读者可据此自由切分。

**已落地**：卷 08 第 1、2 章已按此格式补写 `§0 本章承诺与读法`（2026-09-10）。模板见 `../../templates/Chapter-Contract.md`。

**仍未决**：单章 60–90 分钟是否为全 14 卷的合适上界，还是应在部分卷（如卷 04、卷 07）采用更短的章。见 `../../04-待验证与决策队列.md` P1-AA。

### 10.1 难度曲线（本项目新增）

每卷的章节难度分布应为：

```text
第 1–3 章     建立期：概念清晰、零前置、必须能跑通一个小结果
第 4–N-2 章   爬升期：引入复杂度、失败模式、多来源对照
第 N-1 章     整合期：Spine Case 收束，全部概念一起用
第 N 章       迁移期：方法论升华 + 开放问题 + 下一卷入口
```

**反模式**：把最重要或最难的概念放在第 1 章（读者会放弃）；把 Spine Case 全部放在最后（读者没机会建立直觉）。

### 10.2 模板资产库

每卷需提供一份**可复制资产**（对应样本 B 的任务模板库）：

| 卷 | 模板资产（示例） |
|---|---|
| 04 | 任务说明书模板 / 交付物验收清单 / PKM 目录结构 |
| 07 | 项目脚手架 / 任务模板库 / 交付检查清单 |
| 08 | Agent Task Specification / 最小系统卡 / Eval 规则表 |
| 09 | Harness 配置清单 / 指令层级模板 |
| 10 | Context 预算表 / Memory 策略卡 / Skill 模板 |

**判据**：读者一年后回来，只取这一份文件就能继续干活。

## 11. 14 卷编排总表
