# 07 踩坑与运维经验（2026-09 全量上线战役沉淀）

状态：`WORKING`（持续追加）
沉淀日期：2026-09-28
来源：136 门全量上线战役（2026-09-19 至 09-20，见 `../部署记录/`）

本文是部署与构建过程中实际踩过的坑的完整清单。每条都是真实发生过的事故或返工，不是理论风险。新接手的人先把本文读一遍，能省掉几天返工。

## 一、数据安全类（会丢数据）

### 1. 擦除半径必须等于推送半径

按"卷"擦除服务器目录、却只推"清单内"课程，把清单外已完整的课程一并删掉——2026-09-20 曾因此误删 66 门已上线课程。修复后所有部署工具一律**按课程粒度擦除**（见 `../scripts/deploy/local-tools/volpush.mjs`）。任何新写的同步脚本，先问一句：这个 rm 的范围和我要写的范围完全一致吗？

### 2. 部分构建的产物不能覆盖完整站点

增量批次的产物只含部分课程。用 `rsync --delete` 把它整目录推上去，等于用残缺覆盖完整。部署永远用"按课程/按课程组"的精确路径，不要整树覆盖。

### 3. lib 全程受 Git 跟踪是最后的安全网

本战役中 lib 曾三次被暂存舞步事故弄残（文件进了 `.slice-*` 错位目录、批量"丢失"），全部靠 `git checkout -- site/docs/lib` + `git clean` 恢复。**不要把可再生成但成本高的目录排除出 Git**——lib 的 24,585 个 md 就是这么救回来的。

### 4. 恢复脚本要先假设"两边都有、且都可能是对的"

进程被硬杀后，同一课程的文件可能同时存在于 lib 和暂存区。按"移动归位"写的恢复脚本会撞 EEXIST；按"字节比对合并"写的才能安全收敛（见 `local-tools/recover-stash.mjs`）。

## 二、构建过程类（会构建失败或产错页）

### 5. build-batches 的暂存舞步期间，lib 是禁区

build-batches 每个批次会把非本批课程 rename 进 `.batch-stash`，结束再 rename 回来。期间对 lib 的任何并发访问（跑检查脚本、git status 之外的写操作、第二个构建）都会引发：EPERM 句柄冲突、批量暂存错乱、计数错乱。**单任务纪律：构建跑着的时候，人走开。** 曾因在流式构建期间跑了搜索索引重建，导致连续 9 门课 EPERM 失败。

### 6. 页数估算只看顶层文件会严重失真

官方文档类课程是深层嵌套目录（1,490 页的课程顶层可能一个 md 都没有）。按顶层文件数估批次大小，实际渲染页数会大一个数量级，内存随之爆炸。大体量课程必须走 build-batches 的切片模式（`MAX_PAGES`），或 volpush 的 ≤500 页分组。

### 7. 内存不够时，调大 heap 没用

本机 15.7GB 内存被 QEMU 虚拟机、OneDrive、Defender 等挤占后，空闲只剩 0.9-4GB。此时 `--max-old-space-size` 调到 8G、12G 都没用——失败的是**物理内存**分配（退出码 134 / 3221226505），不是 V8 堆上限。出路三条：切片（`MAX_PAGES=50~200`）+ 免压缩（`TB_NO_MINIFY=1`）+ 错峰重试；或者干脆**在服务器上构建**（见"五、替代路径"）。

### 8. config.mts 的三元 await import 两个分支都会被 esbuild 静态打包

```ts
const catalog = process.env.TB_BATCH_CATALOG === '1'
  ? await import('./theme/generated/catalog-batch')
  : await import('./theme/generated/catalog')
```

运行时环境变量只决定**执行**哪个分支，但**编译**时两个目标文件都必须存在，否则 `Could not resolve` 直接构建失败。目录换装时要把 `catalog.ts` 和 `catalog-batch.ts` 两个文件都换掉。这个坑让构建莫名其妙失败了三次。

### 9. SKIP_MIRROR 模式的 /mirror/ 别名必须指向真实存在的目录

别名若指向 `.mirror-build-stash`（只在 build-batches 的镜像暂存流程里才存在），直接调 vitepress 构建时 Vite 会把图片当模块解析，文件缺失即失败。已改为别名直接指向 `public/mirror`（与 build-batches 的产物形态一致：引用到的图片解析成哈希资产进 assets/）。

### 10. 主题组件直读全量 catalog，增量部署不会刷新它们

`CourseLibrary.vue` 等组件直接 `import './generated/catalog'`。只推课程页的增量部署永远不更新课程库页/首页统计/路径页卡片。要做"索引页与实际上线集一致"，必须换装过滤目录后重建索引页，并同步手工维护的三处硬编码：`paths/*.md` 的表格行与数量句、`library/index.md` 的课程数。

## 三、跨机与进程类（Windows/WSL 特有）

### 11. 带空格的路径是万恶之源

- `spawnSync(cmd, [绝对路径], {shell:true})`：路径在空格处被拆开，`E:\claude code` 变成 `E:\claude`；
- PowerShell `Start-Process -ArgumentList`：含空格的参数被重新分词；
- 对策：spawn 一律用**相对路径 + cwd**；长任务启动脚本放**无空格路径**（如 `C:\Users\DELL\run-xxx.ps1`）。

### 12. WSL VM 会在调用间隙回收，/tmp 不持久

两次工具调用之间 WSL 可能整个重启：/tmp 里放的脚本消失、setsid/nohup 的后台进程被杀。长任务要由一个**独立存活的 Windows 进程**承载（`Start-Process powershell -File ... -WindowStyle Hidden`），或者复制脚本与启动在同一次 WSL 调用内完成。

### 13. WSL 的 swap.vhdx 扩容警告 = 物理内存将尽的前兆

见到它就该停下构建，先释放内存（关 QEMU 等负载）或改道服务器构建。

### 14. 服务器 sshd 会对高频连接节流

几分钟内几十次 ssh 会触发 `kex_exchange_identification: Connection reset`。推送步骤必须带重试（3 次、间隔 45 秒起），失败的推送不要让它静默带崩整个驱动（抛异常要能被捕获并继续下一组）。

## 四、部署与运维类

### 15. hashmap/assets 是"合"不是"替"

图片尺寸映射 `hashmap.json` 与前端 `assets/`（哈希文件名）应增量合并，服务器已有条目打底；整体替换会丢掉其它课程的条目。

### 16. 服务器侧构建是低内存机器的正规出路

最小仓库子集 rsync 到服务器 `/opt`（约 194MB）→ `npm ci` → 镜像目录**软链现网** `/var/www/ai-native-textbook/mirror`（图片零传输）→ 50 页切片 + `TB_NO_MINIFY` + 临时 swapfile → 就地安装 → 还原临时改动。1,500 页单课全程约 1 小时，本机零内存压力。

### 17. 每次部署：先备份、后动手、留记录

服务器保留整站备份 `/var/www/ai-native-textbook-backup-<主题>-<日期>`（现有 5 个）；部署后写 `部署记录/`。这不是仪式——本战役至少三次靠备份/记录回溯事实。

### 18. 大量小文件跨广域网传输用 tar 流，不用 rsync

41,736 个 raw 文件 rsync 拖在往返延迟上；`tar czf - | ssh "tar xzf -"` 一次到位（1.3GB 十几分钟）。

## 五、替代路径速查

| 困境 | 出路 |
|---|---|
| 本机内存不足以构建 | 切片 + 免压缩 + 错峰；或服务器侧构建（坑 16） |
| 构建中途被杀，lib 残缺 | `node scripts/deploy/local-tools/recover-stash.mjs` → `git checkout -- site/docs/lib` → `git clean -f` |
| 换电脑从头接手 | 仓库根 `RESTORE.md`，里程碑 tag `v1.0-full-20260920`，19 个非 Git 来源快照在同名 Release |
