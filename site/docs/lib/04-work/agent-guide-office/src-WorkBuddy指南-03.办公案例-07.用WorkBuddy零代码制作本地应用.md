# 用 WorkBuddy 零代码制作本地应用：需求、运行与排错

很多人都有过做一个小工具的念头。

需求通常不复杂。

能新增一条记录，按关键词搜索，改错字，再给内容分个类，就已经够日常使用。

可一旦准备动手，页面、数据保存和运行环境都会冒出来。没有开发经验的人很难知道该从哪里开始。

WorkBuddy 可以根据自然语言生成代码，并尝试把项目运行起来。

你不用从空白文件开始写程序，可以把精力放在需求、测试和修改上。

这里的「零代码」指用户可以用自然语言推进开发，不代表应用内部没有代码，也不代表生成以后无需检查。

功能能否正常使用、数据保存在哪里、报错有没有修好，仍然要亲自确认。

下面用一个本地知识管理工具，把从第一版到后续修改的过程走一遍。

## 第一版只解决四件事

做小工具最容易犯的错误，是第一次就把所有想法塞进去。

登录、同步、提醒、智能搜索和手机录入一起上，任何一个环节出错都可能让整个项目停住。

先把范围压小。这个示例只做四项核心功能。

- 新增一条记录
- 搜索已有记录
- 编辑记录内容
- 按分类查看内容

这四项可以组成一条完整的使用过程。先记下一段内容，再把它找回来，发现有误时能够修改，记录变多以后还能按类别查看。

第一版跑通这条过程，应用已经可以用来验证想法。

开始前，最好为项目单独建一个空文件夹。

不要直接选择放有重要资料的目录，也不要让生成过程随意改动其他项目。

已有文件需要参与测试时，先准备副本。

## 新建任务时选择代码开发模式

为了让 WorkBuddy 按开发任务处理需求，新建任务时选择代码开发模式，再开启新的对话。

![](https://vtang.oss-cn-hangzhou.aliyuncs.com/images/2026/08/25/20260825T122800Z-a93735eca29c21dc-520c43a3.png)

接下来不要只说「做一个知识库」。

把应用运行位置、主要功能、界面要求和完成标准一起写清楚。

```text
请在当前项目文件夹中制作一个本地可运行的知识管理小工具。

第一版支持新增、搜索、编辑和分类四项功能，适合个人记录工作笔记。界面保持简洁，首页能够看到已有记录和新增入口。

请直接生成所需代码并尝试运行。不要读取或修改当前项目文件夹以外的文件。

完成后告诉我启动方式、数据保存位置和已经实现的功能。遇到无法确认的需求时先保留简单方案，不要自行增加登录、联网或云端同步。
```

这条指令把项目范围和文件边界都写了进去。

第一版不接账号系统，也不主动联网，先确认新增、查找、修改和分类能不能正常工作。

WorkBuddy 根据需求生成代码并运行后，可以在本地打开应用查看结果。

![](https://vtang.oss-cn-hangzhou.aliyuncs.com/images/2026/08/25/20260825T122803Z-be482c3f6babca93-f57e38f2.png)

页面能打开，只能说明应用已经启动。

接下来还要用真实操作检查功能。

## 按照正常使用顺序测试一遍

测试时先新增两三条内容，并给它们设置不同分类。

刷新页面后，检查刚才的记录是否还在。

随后搜索其中一个关键词，打开结果修改内容，再回到列表确认修改是否保存。

这一遍至少要看下面几项。

- 新增后是否立即出现在列表中
- 刷新或重新打开后内容是否保留
- 搜索能否找到标题和正文中的关键词
- 编辑后是否保存最新内容
- 分类切换是否显示正确记录
- 空内容、重复标题等情况是否有合理提示

不要为了测试方便只录入「测试一」「测试二」。

准备几条接近日常笔记的内容，搜索和分类问题会更容易暴露出来。

如果第一版已经满足核心需求，可以先停在这里。

界面颜色、动画和更多按钮不会替代基本功能，先保证数据能保存、能找回、能修改。

## 出现报错时，把现象说完整

本地应用第一次运行出现报错很常见。WorkBuddy 可以继续根据当前项目和会话排查，但需要知道错误是怎么发生的。

只说「不能用」提供不了多少线索。

最好写清触发步骤、页面现象和错误信息。

```text
请检查并修复当前项目中的问题。

我打开一条记录，修改正文后点击保存，页面随即变成空白。这个问题每次都能复现。

控制台出现 TypeError。请先定位原因，只修改与这个报错有关的代码。修复后重新运行，并说明你验证了哪些操作。
```

如果有控制台日志、报错页面或终端输出，可以直接提供截图。

错误信息要尽量完整，不能只截最后一行。首次修改没有解决时，再补充最新现象，让 WorkBuddy 沿着当前问题继续查，不必新建会话重新讲一遍项目背景。

修复完成后，重新执行刚才那组动作。

能保存一次还不够，连续修改两条记录，再刷新页面确认数据仍然存在。

原来的问题解决了，也要顺手检查新增和搜索有没有受到影响。

## 每次只增加一类功能

第一版稳定以后，再考虑升级。

如果精确关键词经常搜不到内容，可以提出模糊搜索或语义检索需求。

如果希望每天查看待处理记录，可以增加自动汇总任务。

需要通过 QQ 或微信录入内容时，则要继续配置相应的消息连接和输入方式。

这些升级的复杂程度不同，可能涉及额外组件、连接器或权限。

不要一次全部加入。先挑当前最影响使用的一项，并把验收方式写进指令。

例如，可以先改善搜索。

```text
请为当前知识管理工具升级搜索功能。

保留现有的新增、编辑和分类功能。搜索时除了匹配精确关键词，也要尽量找到意思相近的记录。

请先说明准备采用的本地方案和需要新增的依赖，再开始修改。升级完成后，用几组含义相近但用词不同的内容测试搜索结果。
```

如果下一步准备增加每日任务提醒，也可以单独开一轮修改，写清执行时间、待办筛选规则和展示方式。

移动端录入则要先确认准备接入的平台和权限，不要在需求还没有定下来的时候让项目同时改动多处。

## 保存一份能回退的版本

每完成一项稳定功能，都建议保存当前版本。

可以复制整个项目文件夹并标记日期，也可以使用版本管理工具记录改动。

后续升级出现问题时，有一份已知可用的版本，就能对照修改，也可以先恢复使用。

否则连续改过几轮以后，很难分清错误从哪一次开始。

还要记下启动方式、数据保存位置和额外依赖。隔一段时间再次打开项目时，这些信息比一张完成截图更有用。

## 写在最后

第一次练习时，选一个只给自己使用的小工具。

把功能控制在三到四项，建好独立项目目录，让 WorkBuddy 生成并运行第一版。

页面打开以后，新增几条真实内容，刷新、搜索、编辑，再检查分类。

遇到问题就把操作步骤和错误信息交给它修。等这一版连续使用没有明显问题，再加下一项功能。

这样做出来的应用也许很小，但每一项功能都经过自己确认。对本地工具来说，能稳定解决眼前的问题，已经足够作为第一版。
