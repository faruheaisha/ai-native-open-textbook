# 12 生产交付和团队协作

## 学习目标

你将理解一个 Dify 应用从 Demo 到生产，需要补哪些工程和协作环节。

## Demo 和生产的差别

Demo 只需要证明“能跑”。生产需要证明：

- 能稳定回答。
- 能处理异常。
- 能控制成本。
- 能保护数据。
- 能追踪问题。
- 能持续维护。

## 角色分工

| 角色 | 负责内容 |
| --- | --- |
| 产品 | 场景、用户、验收标准 |
| 业务专家 | 资料准确性、边界判断 |
| AI 应用设计者 | Prompt、流程、知识库、评估 |
| 开发者 | API 集成、权限、日志 |
| 运维 | 部署、备份、升级、监控 |

## 上线前检查

- 应用目标清楚。
- 用户范围清楚。
- 知识库资料经过审核。
- Prompt 有拒答边界。
- 测试集覆盖主要场景。
- API Key 安全存放。
- 日志和反馈渠道可用。
- 有人工兜底流程。

## 版本管理

每次修改都要记录：

- 修改日期。
- 修改人。
- 修改内容。
- 修改原因。
- 影响范围。
- 回滚方式。

建议维护一个应用变更日志，即使只是 Markdown 表格。

## 知识库维护

知识库不是上传一次就结束。

需要定期检查：

- 是否有过期政策。
- 是否有重复内容。
- 是否有用户经常问但资料缺失的问题。
- 是否有回答错误但资料本身导致的问题。
- 是否需要拆分公开资料和内部资料。

## 成本控制

控制成本的方法：

- 选择合适模型，不是所有节点都用最强模型。
- 固定流程优先 Workflow。
- 控制 Agent 最大迭代次数。
- 控制 Top K 和 Rerank 使用。
- 对高频问题做缓存或 FAQ。

## 交付文档

每个生产应用建议包含：

- 应用说明。
- 用户范围。
- 数据来源。
- 不回答范围。
- 测试集。
- API 文档。
- 维护人。
- 回滚方案。
