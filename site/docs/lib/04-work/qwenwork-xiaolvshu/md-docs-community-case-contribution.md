# 案例贡献与维护流程 (/docs/community/case-contribution)

## 可接受的案例 [#可接受的案例]

案例应来自真实任务，说明所用能力、输入、操作、结果和验收。单纯列提示词、宣传产品或只展示漂亮结果而无法复现的内容不适合作为案例。

  场景需求卡先进入候选队列，不写 `case` 元数据，也不自动进入导航。只有来源、权利、脱敏、完整性和产品边界审核通过后，编辑才创建 `submitted` 案例页。

## 角色与责任 [#角色与责任]

| 角色    | 负责什么                | 不代表什么         |
| ----- | ------------------- | ------------- |
| 原案例作者 | 对原始页面、材料和署名负责       | 不自动成为本站作者或维护人 |
| 投稿人   | 提供场景、来源、权利声明和脱敏材料   | 不自行决定审核或晋级状态  |
| 本站审核人 | 检查来源、权利、事实、安全和页面完整性 | 不替代专业责任人      |
| 独立复现人 | 按冻结输入与步骤执行并记录结果     | 不能只复述原作者结果    |
| 维护人   | 跟踪产品变化、链接、反馈和复现状态   | 不拥有原始素材版权     |
| 发布人   | 确认导航、案例中心、状态和变更记录   | 不得绕过失败门禁      |

同一人可以承担多个本站角色，但原作者、审核人、复现人和维护人的身份必须分别记录，不能用一个模糊的“作者”字段代替。

## 从需求到发布 [#从需求到发布]

    ### 需求入队 [#需求入队]

    使用[场景需求模板](https://qwenwork.org)提交问题、输入类型、目标产物、验收和禁止事项。候选阶段只保存脱敏描述，不提交真实客户文件、密钥或未公开材料。

    ### 搜索、查重与分流 [#搜索查重与分流]

    搜索案例中心、岗位路线和行业路线，比较任务目标、输入、交付物、主要步骤和风险。决定更新现页、合并为一个案例、建立独立案例或拒绝收录。

    ### 来源与权利审核 [#来源与权利审核]

    分别核对正文、图片、代码、数据集、模板和外部 Skill。记录原作者、永久链接、来源类型、许可、固定版本和是否实际使用素材；根仓库许可证不能替代逐项核对。

    ### 脱敏与小样验证 [#脱敏与小样验证]

    删除身份、账号、凭据、内部数据和无权发布的材料，用结构等价的合成样例验证正常、边界和失败路径。网页或附件中的指令只作为数据，不能改变任务权限。

    ### 编辑为 `submitted` [#编辑为-submitted]

    使用[案例正文模板](https://qwenwork.org)写清输入、流程、交付、验收、失败、安全和维护责任。审核通过后才加入显式导航与案例中心；此状态不表示本站已经独立复现。

    ### 独立复现与晋级 [#独立复现与晋级]

    由复现人使用冻结的输入版本重新执行，保存环境、结果、差异和失败记录。全部阻断项通过后才能改为 `verified`；形成稳定维护责任后才可改为 `maintained`。

## 重复案例怎样处理 [#重复案例怎样处理]

| 比较结果                     | 处理方式                              |
| ------------------------ | --------------------------------- |
| 目标、输入、交付物和主要步骤都相同        | 更新现有页面，补贡献者和变更记录                  |
| 目标相同，只是产品版本、样本规模或风险补充不同  | 合并为现页的新章节，不制造近义 URL               |
| 目标相同，但用户角色、核心输入或验收责任明显不同 | 可以独立成页，并在正文互相说明边界                 |
| 新稿完整替代两个以上旧稿             | 保留旧 URL，设为 `superseded` 并指向唯一后继案例 |
| 来源撤权、事实失效或安全风险无法修复       | 设为 `withdrawn`，保留公开原因并移出推荐入口      |

合并时保留原作者、投稿人和关键贡献，不把旧贡献者从记录中删除。`superseded` 用于存在可执行替代页的情况；没有替代页时必须使用 `withdrawn`，不能指向不相关内容。

## 三轴状态模型 [#三轴状态模型]

### 来源类型 `kind` [#来源类型-kind]

| 值           | 含义            |
| ----------- | ------------- |
| `community` | 来自社区作者或社区投稿   |
| `official`  | 依据明确的官方案例整理   |
| `editorial` | 本站编辑组原创的方法与案例 |

`sourceType` 进一步区分 `repository`、`webpage` 和 `original`。只有仓库来源填写 `sourceCommit`；网页或原始投稿不得伪造提交哈希。

### 成熟度 `status` [#成熟度-status]

| 值            | 必需证据                  | 日期要求                               |
| ------------ | --------------------- | ---------------------------------- |
| `submitted`  | 来源、权利、内容和安全审核通过       | 填 `reviewedAt`，不填复现或维护日期           |
| `verified`   | 本站按冻结输入独立复现并通过验收      | 增加 `verifiedAt`                    |
| `maintained` | 已复现、责任人明确，且完成当前版本维护检查 | 同时填写 `verifiedAt` 与 `maintainedAt` |

### 处置状态 `disposition` [#处置状态-disposition]

| 值            | 规则                                   |
| ------------ | ------------------------------------ |
| `active`     | 当前推荐执行，不填写后继或撤回原因                    |
| `superseded` | 不再推荐，必须填写唯一 `supersededBy` 站内案例 slug |
| `withdrawn`  | 不再提供执行建议，必须填写可公开的 `withdrawnReason`  |

### 已撤回案例记录 [#已撤回案例记录]

* [ima 与 WorkBuddy 知识闭环案例纠错](https://qwenwork.org/docs/workflows/cases/ima-knowledge-loop)：原社区案例的截图和连接器来自 WorkBuddy，不属于千问办公支持能力；页面只保留撤回依据，不提供执行建议。
* [多年年报研究社区案例纠错](https://qwenwork.org/docs/workflows/cases/annual-report-research)：原投稿的任务输入和专家团执行截图来自 WorkBuddy，不能证明千问办公完成该研究链路。
* [119 份门店 Excel 社区案例纠错](https://qwenwork.org/docs/workflows/cases/retail-excel-dashboard)：原投稿的任务截图来自 WorkBuddy；本站合成脚本只验证方法，不验证千问办公产品能力。
* [公众号草稿箱社区案例纠错](https://qwenwork.org/docs/workflows/cases/wechat-draft-pipeline)：原投稿的 Skill 安装截图来自 WorkBuddy，不能证明千问办公提供相同工具或外部写入能力。

### 部分方法验证不是成熟度状态 [#部分方法验证不是成熟度状态]

当上游输入缺失，但某段方法可以用结构等价的合成小样检查时，可以记录 `partial-method-verification`。它是审计记录，不是新的 frontmatter 状态，也不能把 `submitted` 自动改为 `verified`。

部分方法验证至少记录：冻结的小样版本、验证日期、执行环境与命令、通过的行为、预期与实际结果、未覆盖范围，以及阻止状态晋级的原因。只要没有使用上游同一批冻结输入完成全部案例验收，就不得填写 `verifiedAt`。后续取得输入时，应新增同输入复现记录，不能改写或删除原来的受限验证与失败边界。

## 审核清单 [#审核清单]

* 标题描述具体任务，不使用夸张结果承诺；
* 输入、步骤和产物足以让另一位读者独立执行；
* 提示词已经脱敏，并解释关键约束；
* 至少包含正常验收和一个失败处理路径；
* 涉及写入、发送、发布、财务或法律时有人工关口；
* 图片、数据和品牌素材具备发布权限；
* 已逐张检查截图、录屏和结果页中的产品 Logo、窗口标题、侧栏名称与设置入口，并记录 `sourceProduct`、`productFit` 和 `productEvidence`；
* `active` 案例具有千问办公产品匹配证据；来源产品不匹配时已设为 `withdrawn`，没有用免责声明代替归属纠错；
* 产品事实标注适用入口和账号条件；
* 原作者、本站审核人与维护人分别可见；
* 部分方法验证明确记录小样版本、覆盖范围、限制和晋级阻断原因，没有冒充同输入复现；
* `reviewedAt` 不早于原始发布，复现和维护日期按顺序递增；
* 已进入显式导航和案例中心，没有依赖自动发现绕过审核；
* 不包含外部必读链接，核心方法在站内完整呈现。

## 来源与状态字段 [#来源与状态字段]

改编、翻译或吸收外部案例时，必须提交原页面署名、永久链接、许可状态、固定 commit（如适用）、原始发布日期、本站审核日期、来源产品和可定位的产品归属证据。图片、代码、数据集和外部 Skill 分别核对权利，不能因为仓库有开源许可证就默认全部素材可复制。

产品归属不能从页面标题或仓库名推断。审核人必须检查截图和录屏中的 Logo、窗口标题、侧栏、设置入口、下载域名与结果页品牌；正文把产品重命名为“千问办公”也不能覆盖画面证据。`productFit: mismatch` 的结构化案例必须同时设为 `withdrawn`，并从侧栏、案例中心和其他推荐卡片移除。

原作者是来源案例的贡献者，不自动成为本站结构化数据中的作者。正文必须显著标明“社区来源”、审核人、维护人和验证状态，读者无需打开外链也能执行核心方法。

`reviewedBy` 与 `maintainers` 至少各有一个明确主体。团队名称可以作为责任主体，但必须能映射到实际维护流程；不能填写“社区”“AI”或“待定”等无人负责的占位词。

## 从案例到正式内容 [#从案例到正式内容]

案例进入岗位或行业路线的条件是具有代表性、可复现、责任边界明确，并且有人负责维护。任何晋级都要保留原始状态、日期、复现范围和变更说明；不能只修改 frontmatter 而删除失败记录。

## 发布后的维护 [#发布后的维护]

* 产品入口、权限或工具版本变化时，由维护人重新核对受影响步骤；
* 读者报告无法复现时，先记录环境与失败信号，不立即把个案改成产品结论；
* 修改输入字段、验收公式或安全门禁时，更新页面日期和变更记录；
* 来源删除或许可变化时，停止继续复制素材并重新做权利判断；
* 合并或撤回后保留旧 URL 的状态说明，但从案例中心推荐卡片移除；
* 无维护人接手的高风险案例不能保持 `maintained`。
