# 第 9 章 技能与规则：双层 SKILL.md 与 WORKBUDDY.md

技能（Skill）是 WorkBuddy 用户最先接触的定制手段，也是最被低估的。装一个「深度调研」技能，助手突然会做证据审查了；装一个「公众号排版」技能，产出直接符合栏目规范。规则文件则是它的沉默搭档：项目根目录放一份说明文件，助手在这个项目里的行为就变了。

这一章讲清两件事的文件形态与生效机制，并带你在十五分钟内写出第一个能用的技能。读完本章，你应能解释技能与规则的区别、双层技能目录的叠加关系，并完成一次安全的定制。

## 9.1 技能是什么：一段按需加载的方法论

先破除一个误解：技能不是代码。技能的主体是一份 Markdown 文档——SKILL.md，开头一段元数据（名字、一句「什么时候用我」的描述），正文写「这类任务怎么做」。模型在对话中判断当前任务匹配某个技能的描述时，读取该文档并遵循其中的方法。

这个设计的关键词是**按需加载**。系统提示词寸土寸金（第 5 章），技能清单只把「名字+描述」放进基础上下文——一行一个；完整方法论文档等你真的做这类任务时才读取。官方把这归入编排层的渐进式加载：用一份目录换一整座图书馆的按需取用。

动手看自己的技能库：

```
ls ~/.workbuddy/skills/ | head -20
head -8 ~/.workbuddy/skills/<某个技能名>/SKILL.md
```

第二条例子里你会看到每份技能的「门牌」：frontmatter 里的 name 和 description。**description 是技能的命脉**——模型凭它决定何时唤醒这个技能。写技能的一半功力在写好这一句话：具体、带触发词、划清边界（「用于……，不用于……」）。

## 9.2 双层目录：用户级与项目级

技能存在两个层级：用户级 `~/.workbuddy/skills/`（全项目可用）和项目级 `/.workbuddy/skills/`（仅当前项目）。实测本机一个真实项目：项目级 97 个技能是用户级 101 个的子集，同名文件内容完全一致——项目目录像是用户库在这个项目里的同步副本，加上项目特有的技能。

这个设计的意图是隔离：工作项目的技能不污染个人项目，反之亦然。给团队分发规范时，把技能放进项目目录随代码仓库走，每个成员打开项目即得同一套方法——这是把「组织知识」版本化的正确姿势。

优先级问题（同名技能两层都有时用谁的）本机未取得运行时样本，这里给读者留一个十五分钟的受控实验，顺带验证整章机制：

```
LABDIR=$(mktemp -d /tmp/skill-lab.XXXXXX)
mkdir -p "$LABDIR/.workbuddy/skills/demo-probe"
```

在 demo-probe 下写一个最小 SKILL.md（name 用一个你在用户级没有的词，description 写「当用户说『探针』时，回复『项目级技能已激活』」），在 WorkBuddy 里打开 $LABDIR 目录作为项目，说「探针」。然后把这个技能复制进用户级、改掉回复文案，再问一次——两次回答的差异就是优先级的直接证据。实验完删除临时目录即可。

## 9.3 规则文件：项目的宪法

技能管「怎么做某类任务」，规则管「在这个项目里永远遵守什么」。官方工程复盘提到的约定是：项目根目录放规则文件（社区与官方材料中出现的名字包括 WORKBUDDY.md，与开发者工具通用的 AGENTS.md 同族），记录架构约定、依赖边界、安全要求、代码风格；子目录可以放局部规则做更细的约束，原则是「项目规范放工作区规则文件」。

规则与技能的生效机制不同：**技能按需进入，规则常驻在场**。规则文件的内容在相关项目的每次请求里都会被注入（引导层资产）。这决定了两者的写作纪律——规则要短、要硬、要可执行（「提交信息用中文，格式：动词+对象」），技能可以长、可以软、可以讲道理（「做调研时优先找一手来源，理由是……」）。

实践中最常见的错误是拿规则当技能写：把一大段「如何做 X」塞进规则文件，结果每次请求都背着这段负重，模型反而抓不住重点。判断标准一句话：**「永远适用」进规则，「有时适用」进技能**。

## 9.4 十五分钟：写你的第一个技能

现在写一个真正有用的。选一个你重复解释过三遍以上的偏好或流程——比如「周报格式」。在用户级建目录：

```
mkdir -p ~/.workbuddy/skills/weekly-report-style
```

写 `~/.workbuddy/skills/weekly-report-style/SKILL.md`：

```
---
name: weekly-report-style
description: 周报写作规范。当用户要求写周报、周总结、weekly report 时使用。不用于日记、月报或项目复盘。
---

# 周报规范

结构三段：本周结论（3 条以内）、数据变化（带数字）、下周计划（按优先级）。

规则：
- 每条一行，动词开头，不写套话
- 数字必须来自用户提供的材料，缺失就标注「待补」
- 总长度不超过 300 字
```

保存后开新会话说「帮我写周报」。如果它按三段结构出稿，链路就通了；如果没触发，九成是 description 不够明确——改那句触发条件，再试。这就是技能开发的完整循环：写门牌、写正文、实测、改门牌。

进阶方向：正文里可以引用同目录下的参考文档（子文件放模板、示例），技能目录是一个小知识包而不必是单文件；官方市场里的成熟技能（如文档处理套件）是最好的范文。

## 9.5 边界

本章边界：双层目录的同步关系基于单项目实测，优先级结论待读者实验补全（9.2 的受控实验即为此设计）；规则文件的名字与作用域约定来自官方工程复盘与社区材料，5.3.13 本机未预置示例文件；「按需加载」的内部触发机制（是模型自主判断还是框架拦截）不可观测，两种解释在社区材料中并存，本书按「描述匹配」的行为层理解。

至此，扩展系统的三层（专家、插件、技能）讲完。下一章换视角：不看你给了它什么，看它留下了什么——会话、轨迹与审计，Harness 的反馈层与你的证据现场。
